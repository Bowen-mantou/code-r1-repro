# GPU 显存指南：RL 训练显存账的完整方法论（01）

> 以本项目 A800 80GB 实战为案例：显存从哪来、怎么算、怎么压、OOM 怎么查。
> 核心原则：**显存账必须引用实测，不能靠权重+KV 推算**（我们用 ¥3.3 学费验证过）。

---

## 一、显存墙：为什么 3B 模型也吃满 80GB

```
显存 = 参数系（静态） + 激活系（动态） + 推理引擎（vLLM KV）

参数系（3B 全参）：
  权重 bf16       6.2GB
  梯度 bf16       6.2GB
  Adam 状态 fp32 12.4GB（m、v 各 4 字节/参数）
  小计          ~25GB

激活系（batch 相关，RL 的最大变量）：
  前向激活（无优化）  = batch_tokens × hidden × layers × 常数
  梯度检查点后        ≈ 前者的 30-40%（重算代价：+30% 计算）
  FSDP all-gather 权重副本 + 通信 buffer

推理引擎：
  vLLM KV 池 = util 0.25 × 80G ≈ 20G（实际 ~13.6GB）
```

**我们的实测账（E7/E9p2 双卡）**：
```
卡 0：worker 峰值 58.6GB（含 ref 换入 + KL 前向）
    + vLLM KV 13.6GB
    = 72.2GB / 79.25GB 可用 → 压线（token_len 2560 的由来）
卡 1：verifier 1.5B = 4GB
```

**反直觉点（面试）**：权重只有 6GB，但 Adam 状态 12GB、激活 20-30GB——**优化器状态
是权重的 2 倍**，这是全参微调最容易被忽视的隐性成本。

## 二、五类 OOM 与各自的修法（分类学）

| OOM 类型 | 特征 | 修法 |
|---------|------|------|
| 激活 OOM | 前向/反向某层 alloc 失败 | 梯度检查点、token_len 降、micro_batch 降 |
| 参数系 OOM | 加载即爆 | offload（Adam 状态出卡）、bf16 化、LoRA |
| 推理引擎 OOM | vLLM 起不来 | util 调小、free_cache_engine、分卡 |
| **共卡竞争 OOM** | 训练与 rollout 交替时爆 | 时序协调 + sleep mode 关 + 清卡逻辑 |
| **碎片 OOM** | 有空间但无连续块 | max_split_size_mb=128 + GC 阈值调低 |

**本项目的三次真实 OOM**：
1. 8 worker 各加载 verifier（8×4GB）→ **设计错误**：先数调用方再设计常驻服务
2. 孤儿 vLLM 引擎残留 19.87GB → 启动前清卡 + 显存断言
3. 碎片化 → PYTORCH_CUDA_ALLOC_CONF（48→42GB，PRO6000 实测）

## 三、压显存武器谱（按代价排序，面试背这个表）

| 手段 | 省 | 代价 | 我们用了吗 |
|------|-----|------|-----------|
| 梯度检查点 | 激活 -60% | 计算 +30% | ✅ |
| forward_prefetch=False | ~2GB | 无 | ✅ |
| ppo_max_token_len 2560 | 激活线性降 | 长样本截断 | ✅ |
| ref param_offload | ref 权重出卡 | 步耗时+（换入换出）| ✅ |
| vLLM util 0.25 | KV 池 20G→13.6G | rollout 吞吐 | ✅ |
| optimizer_offload | Adam 12GB 出卡 | 步耗时++ | 预留 |
| micro_batch 减半 | 激活减半 | 步耗时↑ | 备用 |
| 关 KL | ref 全开销 | 稳定性风险 | ❌ 不砍 |
| LoRA | 参数系 -90% | 表达力 | ❌（全参是设计选择）|

**决策原则**：先零代价（prefetch）→ 再换时间（offload）→ 最后牺牲吞吐（micro_batch）。
每一笔都要能说出代价。

## 四、显存观测工具箱

| 工具 | 看什么 | 我们的用法 |
|------|--------|-----------|
| nvidia-smi | 实时显存（粗粒度）| 轮询 + 清卡断言（<2000MiB）|
| `perf/max_memory_allocated_gb` | 训练进程峰值（**唯一可信的账本来源**）| 每步记录、峰值引用 |
| torch.cuda.memory_summary | 分块明细 | 碎片诊断 |
| 训练日志步耗时 | 间接信号（offload 换入会让步耗时跳变）| 异常检测 |

**教训（PITFALLS #6）**：单卡账本 44GB vs 实测 57.6GB 的差距导致 E2 一次 OOM——
**「引用实测指标，不靠推算」是显存管理的铁律**。

## 五、单卡死刑的两个案例（为什么必须双卡）

1. **OPD 单卡死刑**：worker 37 + 7B teacher 引擎 38-40（其中 ~24GB 是 vLLM 不透明
   固定开销——util 0.25→0.19 只降 1GB）+ rollout 6.2 > 任何单卡容量。
   教训：**给 vLLM 引擎留 20G+ 不可控开销**，显存预算不能只加权重+KV。
2. **Verifier 共卡压线**：58.6+13.6+4=76.2GB 贴 80G——单卡理论可行但零余量，
   任何波动即 OOM。双卡是工程现实而非偏好。

## 六、面试速答模板

「显存管理我有三层方法：**算账**（参数系+激活系+推理引擎，全部引用
max_memory_allocated 实测）、**排序**（压显存手段按代价排序，先零代价后换时间）、
**观测**（三步定位：nvidia-smi 粗查 → peak 细查 → memory_summary 分块）。本项目的
三个 OOM 事故都归档成了分类学条目。」
