# 数据与轨迹处理实战（03）

> 本项目数据管线的全部异常处理经验：下载校验、坏行处置、口径冻结、断点续跑、
> 超长样本。对应 search-r1 版的「异常轨迹过滤」——本项目的对应物在**数据层**。

---

## 一、下载与校验（三个事故换来的规矩）

### 1.1 事故：NUL 空洞（aria2c 稀疏文件）

```
症状：880 行 JSON 里 7 行报 Invalid control character，位置在 4.7MB 处
根因：aria2c --file-allocation=none 用稀疏文件，失败分片留 NUL(0x00) 空洞，
      文件大小却「正确」（稀疏文件逻辑大小不变）
教训：多连接下载必须 --file-allocation=falloc
```

### 1.2 事故：历史 commit 冷对象

```
resolve/{commit} → 60KB/s（无 CDN 缓存，回源）
resolve/main    → 371KB/s~31MB/s（热缓存）
教训：下载前先 curl -sIL 对比 Content-Length，能用 main 就用 main
```

### 1.3 铁律：下完 sha256 对账

```
大小一致 ≠ 内容完整（NUL 洞就是反例）
sha256 来源：HF API ?blobs=true 的官方 LFS oid
```

## 二、坏行处置：静默跳过的危险（口径事故）

### 2.1 事故链

```
gen_lcb.py 曾加「try/except json.loads → continue」容错
→ 坏行被静默跳过 → 题目数 < 880 → 评估口径悄悄改变
→ dry-run（无卡验证）抓到 7 个坏行才暴露
```

### 2.2 正确做法（写进规范）

- 数据加载**严格模式**：坏行 raise，绝不 continue
- 修复数据而不是容忍数据（NUL 洞是下载问题 → 重下，不是解析问题 → 跳过）
- 无卡 dry-run 专项：行数、JSON 合法性、question_id 唯一性、字段兼容性

## 三、口径冻结（六模型可比的根基）

```
1. LCB 880 题 = main 分支 test1-5 并集（2025-06-05 冻结后未变）
2. sha256 冻结 + 每次评估前校验
3. 生成口径：撞顶重跑（hit_cap → 单独 2048）保证与串行逐 token 一致
4. 打分口径：官方 codegen_metrics（16 进程、timeout 6s）
```

**口径事故回顾**：pin commit 0687ab61（以为 main 漂移）→ 实际拿到 584 题的更老版本
→ 全部评估白跑一天。**教训：判断「数据变了」前先查版本历史。**

## 四、断点续跑与超长样本

### 4.1 断点续跑（余额耗尽的保命机制）

```
gen_lcb_fast.py：done_ids 读旧输出 → 只生成缺失题
veRL 训练：latest_checkpointed_iteration.txt → save_freq=32 最多丢 13 分钟
```

### 4.2 超长样本（LCB 的 30MB 单行题目）

```
症状：生成卡在「batch 400/800」15 分钟不动（CPU 100% 在算，非死锁）
根因：单行 30MB 的题面，tokenize + prefill 超长序列
处置：不干预（健康慢算）——但评估时间预估必须把它计入
教训：装箱排序时超长题会被默认长度先验排在最后——「慢题集中爆发」是调度特征
```

## 五、异常检测清单（数据层的三层防线）

| 层 | 手段 | 抓到的 |
|----|------|--------|
| 下载 | falloc + sha256 对账 | NUL 洞、传输损坏 |
| 解析 | 严格模式 + dry-run 专项 | 坏行、缺字段、重复 id |
| 口径 | 版本冻结 + 撞顶重跑 + 官方 harness | 漂移、生成不一致 |
| 监控 | 进度轮询 + CPU 时间对比 | 假死 vs 慢算（CPU 时间≈墙钟=在算）|

## 六、面试速答模板

「数据层的坑我踩全了：下载的 NUL 空洞（稀疏文件）、解析的静默跳行（改口径）、
版本的 commit 漂移（白跑一天）——每个事故都沉淀成了固定防线：falloc+sha256、
严格解析+无卡 dry-run、口径冻结+撞顶重跑。**数据问题永远优先在 ¥0.1/hr 的无卡
模式排查，这是最便宜的一课。**」
